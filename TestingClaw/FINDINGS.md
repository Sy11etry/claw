## F1. Нельзя вернуть параметр, который только читается, и карточка про это молчит

- Серьёзность: **неудобно** (документация). Причина провала 4 из 40 программ экзамена.
- Программа (`min/m1_ret_str_param.claw`):
  ```claw
  fn id(s str) str {
      ret s
  }

  fn main() {
      print(id("hi"))
  }
  ```
- Команда: `claw run m1_ret_str_param.claw`
- Ожидал: `hi`.
- Получил: `E0152 s (line 1) only looks at another value, so it cannot be moved or returned; copy it here or where it is declared; fix: write copy(s)`.
- Что видно: `ret x` для `int` и `ret xs[0]` для `[]int` работают, потому что числа копируются сами. Для `str`, `[]T` и полей структур нужна явная копия. В карточке этого правила нет: там про `copy(a[i])` сказано только для `mut x :=`.
- Фраза «copy it here or where it is declared» неясна: «где объявлено» для параметра значит «в вызывающем коде» или «в функции»? Сообщение советует оба варианта.
- Предложение: в карточке одна строка «параметр только читается, вернуть его можно через `copy(p)`». Карточка сейчас 1999 из 2000 токенов, место надо выкупить.

## F2. E0152 для поля параметра: сообщение не называет выражение, `claw fix` не даёт патча

- Серьёзность: **плохое сообщение**, нет патча.
- Программа (`min/m4_ret_field_param.claw`):
  ```claw
  type P { a int, b str }

  fn name(p P) str {
      ret p.b
  }

  fn main() {
      print(name(P{1, "x"}))
  }
  ```
- Команда: `claw run m4_ret_field_param.claw`, затем `claw fix m4_ret_field_param.claw`.
- Ожидал: `x`, либо патч `copy(p.b)`.
- Получил: `E0152 only a whole variable can be moved; write copy(...), or use remove or swap`. Сообщение не называет выражение `p.b` и не говорит, почему `p` нельзя отдать. `remove` и `swap` здесь не подходят: они для элементов массива, а не для полей параметра. `claw fix` печатает `fixed 0`.
- Вручную `copy(p.b)` работает (проверено: программа `exam/20_pair_template.claw` печатает `1 one`, `one 1`).

## F3. Шаблон компилируется для `int` и падает для `str`, сообщение не говорит почему

- Серьёзность: **плохое сообщение**.
- Программа (`min/m6_template_int_and_str.claw`):
  ```claw
  fn id[T](x T) T {
      ret x
  }

  fn main() {
      print(id(3))
      print(id("pear"))
  }
  ```
- Команда: `claw run m6_template_int_and_str.claw`
- Ожидал: либо оба вызова работают, либо понятно, что `str` не годится.
- Получил: `E0152 x (line 1) ...` на строке тела шаблона. Не сказано, что ошибка появилась для `T = str`. Пользователь видит, что `int` работает, и не понимает почему `str` нет.
- Тело шаблона проверяется для каждого набора типов (это записано в `docs/STATUS.md`, но не в сообщении). Предложение: в сообщении добавить «при `T = str`».

## F4. `claw fix` добавил `+mem` к публичной подписи и ничего не сказал

- Серьёзность: **неудобно**.
- Программа: `exam/19_max_template.claw`, `pub fn max[T](a T, b T) T`.
- Команда: `claw fix` на копии.
- Получил: подпись стала `pub fn max[T](a T, b T) T +mem`, `ret a` стало `ret copy(a)`. Патч сообщает только `fixed 3`.
- Это может быть правильно: копия выделяет память, и подпись говорит правду (принцип 6). Но пользователь не видит, что подпись изменилась. Предложение: `claw fix` пишет «добавлен +mem».
- Для `int` `copy` не нужна, но компилятор проверяет шаблон общим правилом, поэтому `+mem` всё равно появляется.

## F5. `claw fix` починил одну из двух ошибок E0152, вторая осталась без патча

- Серьёзность: **неудобно**.
- Программа: `exam/21_first_or_template.claw`. `claw fix` заменил `ret d` на `ret copy(d)`. Строка `ret xs[0]` с E0152 «only a whole variable can be moved» осталась. Вручную `ret copy(xs[0])` работает (печатает `7`, `none`).
- Патча для элемента массива нет, хотя подсказка `copy(...)` верная.

## F6. SIMD нет ни в карточке, ни в скилле

- Серьёзность: **неудобно** (документация).
- Программа `exam/37_simd_sum.claw` прошла, но имена `f64x2` и `lane` я взял из `docs/SPEC.md`, который видел раньше. В карточке и в скилле есть только имена типов `f64x2 f32x4 i32x4`. Модель без SPEC должна угадывать `vload`, `fma`, `lane`.
- Предложение: в скилле одна строка с функциями SIMD (или ссылка на SPEC).

## F7. `claw test` печатает заметку о переполнении даже в прогонах, где всё прошло

- Серьёзность: **неудобно** (шум).
- Программа `exam/29_test_pass.claw`: два теста проходят, но выводится `note: add overflows for add(1, 9223372036854775807); add a need if that input is not meant to work`. По `docs/STATUS.md` заметка ожидаема. Но в каждом прогоне она напоминает про переполнение, даже если тесты про другое.

# Пункт B: сишные библиотеки

Программы: `TestingClaw/cinterop/`, проверка: `check_c.py` (сборка claw, запуск, сверка с C-эталоном, в том числе x86-64 под Rosetta). Итог: 21 из 26 прошли, 5 падений (это и есть находки F9–F11, F17).

## F8. `__attribute__((packed))` игнорируется: размер структуры расходится с C (сломан код)

- Серьёзность: **сломан код** (тихая ошибка раскладки, самое опасное из найденного в C-интерфейсе).
- Заголовок (`cinterop/broken/bad_attribute.h`):
  ```c
  struct __attribute__((packed)) Pk { char c; int i; };
  ```
- Программа (`cinterop/broken/p6_packed_size.claw`): `ret int(sizeof[Pk]())`.
- Команда: `claw build p6_packed_size.claw`, запуск. Сравнение с C: `sizeof(struct Pk)` тем же заголовком.
- Ожидал: 5 (упакованная структура).
- Получил: **8**. `cdecl` перевёл структуру как `type Pk { c u8, i i32 }`, без упаковки, и не предупредил.
- Последствие: если C-библиотека передаёт или принимает такую структуру, поля будут читаться со сдвигом, без ошибки.

## F9. `sizeof` внутри макроса для размера массива даёт `[0]`, ошибка E0126 указывает не туда (сломан код)

- Серьёзность: **сломан код** для всей библиотеки (curl не собирается вообще) + **плохое сообщение**.
- Минимум (`cinterop/broken/sizes_sizeof.h`, программа `p7_sizeof_array.claw`):
  ```c
  #define NB (sizeof(int) * 8)
  typedef struct { int bits[(1024 + NB - 1) / NB]; } Fds;
  ```
  Без `sizeof` (`sizes_plain.h`, `NB 32`) всё работает: `cdecl` даёт `bits [32]i32`.
- Команда: `claw build p7_sizeof_array.claw`.
- Получил: `cdecl`: `type Fds { bits [0]i32 }`. Сборка: `sizes_sizeof.h:2:17 E0126 array size must be at least 1`. Место указано в строке перевода, а не в заголовке.
- В SDK macOS это `__DARWIN_NFDBITS (sizeof(__int32_t) * __DARWIN_NBBY)` в `fd_set`. Поэтому `curl/curl.h` (через `sys/select.h`) не собирается: `b11_curl.claw`, `curl/curl.h:2:24 E0126`.
- Обход: объявить нужные функции вручную (`extern fn curl_global_init(...)`), см. `b16_curl_extern.claw`: проходит.

## F10. Имена функций с заглавной буквы переводятся с маленькой; вызов по C-имени даёт «unknown function» (плохое сообщение)

- Серьёзность: **плохое сообщение** (и неудобно: правило не записано нигде).
- Программа (`cinterop/b10_bz2.claw`): вызов `BZ2_bzBuffToBuffCompress`.
- Команда: `claw build b10_bz2.claw`.
- Получил: `E0101 unknown function BZ2_bzBuffToBuffCompress`.
- Причина: `cdecl` переводит её как `extern "BZ2_bzBuffToBuffCompress" fn bZ2_bzBuffToBuffCompress(...)`. Первая буква уменьшена, чтобы имя подходило под правило claw «функции с маленькой буквы». То же с `XML_ParserCreate`, которое становится `xML_ParserCreate` (`b13_expat.claw`).
- Обход: писать переведённое имя (`b14_bz2_renamed.claw`, `b15_expat_renamed.claw`): оба проходят. Ошибка должна подсказывать это имя.

## F11. Функции, объявленные макросами (`toupper`, `isdigit`), не переводятся, и это не объяснено (плохое сообщение)

- Серьёзность: **плохое сообщение**.
- Программа (`cinterop/b04_ctype_time.claw`): `use c "ctype.h"`, вызов `toupper(c)`.
- Получил: `E0101 unknown function toupper`. `cdecl` даёт `extern "__toupper" fn c__toupper(...)`, а `isdigit` не появляется вовсе, без строки «not translated».
- Обходы, оба проверены: `c__toupper(...)` (печатает 81) и ручной `extern fn toupper(c i32) i32` (`b06_ctype_extern.claw` проходит).

## F12. `static inline` функции молча пропускаются (плохое сообщение)

- Серьёзность: **плохое сообщение**.
- Заголовок (`cinterop/broken/inline.h`): `static inline int sq(int x) { return x * x; }`.
- Программа (`broken/p5_inline.claw`): вызов `sq(3)`.
- Получил: `E0101 unknown function sq`. `cdecl` выводит пустой перевод: строки «not translated» нет.
- Ожидал: либо понятно «static inline функции не имеют символа в библиотеке, вызвать нельзя», либо такая функция в переводе с пометкой.

## F13. Незакрытый `#ifndef` принимается молча (неудобно)

- Серьёзность: **неудобно**.
- Заголовок (`cinterop/broken/bad_no_endif.h`): `#ifndef ...` без `#endif`.
- Получил: `cdecl` переводит функцию без предупреждения. Для настоящего компилятора C это ошибка.

## F14. Функция, возвращающая структуру по значению (`div`), даёт E0101 без объяснения (плохое сообщение)

- Серьёзность: **плохое сообщение**.
- Программа (`cinterop/b21_div_struct_by_value.claw`): `r := div(7, 2)`.
- Получил: `E0101 unknown function div`. `cdecl` в этом же случае пишет «not translated (struct by value, union or unknown type): div», но компилятор эту причину не повторяет.

## F15. Символ, которого нет в библиотеке, находится только при запуске (неудобно)

- Серьёзность: **неудобно**.
- Программа: `b12_iconv.claw` без `// clw: -l iconv` (iconv в macOS не в libSystem). Вариант: `broken/p1_no_endif.claw` (функция не определена ни в одной библиотеке).
- Команда: `claw build` проходит, затем запуск падает: `dyld: Symbol not found: _iconv_open`, код выхода -6 (аварийное завершение).
- Ожидал: ошибка при сборке, а не при запуске. Компилятор не проверяет, что символ есть в подключённых библиотеках.

## F16. `cdecl` даёт параметрам префикс `c__` и безымянным параметрам `a0`, `a3` (неудобно)

- Серьёзность: **неудобно** (только читаемость, на вызов не влияет).
- Пример: `extern fn strchr(c__s *u8, c__c i32) *u8`, `extern fn time(a0 *i64) i64`, `extern fn XML_Parse(parser *u8, s *u8, len_ i32, isFinal i32) i32`.

## F17. Плоская `fn` принимается как колбэк, хотя документация говорит «от claw fn» (документация)

- Серьёзность: **неудобно** (документация не совпадает с поведением).
- Программа (`cinterop/b19_cb_plain_fn.claw`): `fn cb(x i32) i32` и `cast[*u8](cb)`.
- Получил: сборка проходит. Карточка и скилл говорят «`cast[*u8](f)` от claw fn» и «`claw fn` только для указателей».
- Что решить: либо запретить, либо написать в карточке, что обычная `fn` с числами тоже годится.

# Пункт C: потоки (`par`)

Программы: `TestingClaw/par/`. Важно: `claw run` выполняет задачи по очереди, поэтому гонки проверяются только на бинарниках из `claw build` (скрипт `par/stress.sh`, по 200 запусков на arm64 и на x86-64).

## F18. Функция в переменной даёт две ошибки: вторая непонятна (плохое сообщение)

- Серьёзность: **плохое сообщение** (каскад).
- Программа (`par/c15_fn_value.claw`): `g := square`, затем `par.build(3, g)`.
- Получил:
  - `E0123 cannot tell which function type square should have; write f fn(int) int = square`. Понятно.
  - `E0144 cannot work out R; write build[...](...)`. Вторая ошибка следует из первой. Подсказка `build[...](...)` не объясняет, что писать вместо `g`.
- Ожидал: одна ошибка с подсказкой про явный тип переменной.

## F19. Подсказка для `+io` в задаче неверна (плохое сообщение, вводит в заблуждение)

- Серьёзность: **плохое сообщение**.
- Программа (`par/c10_io_effect.claw`): `fn work(x int) int +io`, затем `par.build(3, work)`.
- Получил: `E0178 work is +io, which this function type does not allow; add +io to the type`.
- Совет «добавь `+io` к типу» не работает: задачам `par` нельзя иметь побочные эффекты, поэтому это не путь. Нужна подсказка «задача не может печатать или читать файлы; вынеси ввод-вывод в основной поток».

## Что работает (для отчёта)

- Результаты `par.map` и `par.build` совпадают с обычным циклом для размеров 0, 1, 2, 7, 1000 и 1 000 000, для `int`, `str` и структур со `str` (`c01_sizes`, `c02_stress`, `c13_empty`).
- 5000 задач, каждая строит строку с интерполяцией: все строки верные (`c03_interp_tasks`).
- 100 000 задач: счётчик и сумма верны (`c12_many_tasks`).
- Деление на ноль внутри задачи: `claw run` и `claw build` дают `trap: division by zero at file:line:col` и код 101 (`c11`).
- Стресс-прогон (`par/stress.sh`): 1700 запусков бинарников из `claw build`, по 850 на arm64 и на x86-64 (c02, c03, c12, c14 по 200 раз, c01 по 50), расхождений и сбоев нет; оба архитектуры дают одинаковый первый результат.
- Замер скорости `par.map` против цикла: сделаю на тихой машине в конце (пункт G), здесь не измерял.
